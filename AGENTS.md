# Syncarr project notes

## Project structure

- `index.py` selects the multi-job engine when `SYNCARR_CONFIG` or indexed multi-job environment variables are set. Otherwise it starts the original single-pair implementation in `legacy_index.py`.
- The legacy configuration remains in `config.py` and `config.conf`.
- The multi-job configuration loader is `multi_config.py`; synchronization and scheduling are in `multi_sync.py`.
- The Docker image currently uses Python 3.6. Keep new code compatible with Python 3.6 unless the image runtime is deliberately upgraded.
- The multi-job mode uses YAML through PyYAML. Endpoint URLs and API keys are supplied through environment variables, not embedded in example configuration files or logs.

## Multi-job configuration decisions

- Legacy jobs remain directional source-to-target rules. Each retains its stable ID, interval, management tag, and existing behavior.
- New directed pairs connect two distinct instances of the same type. A pair has one interval, pair-level defaults, explicit source-to-target quality-profile mappings, root mappings, and any number of stable-ID transfer rules. Rules inherit pair defaults and explicit rule values override them. YAML and indexed environment variables expose the same settings.
- New pairs support Radarr and Sonarr equally. Profile mappings refer to profiles that already exist. Resolve all configured source and target profiles before writing to the affected destination; missing, ambiguous, or conflicting mappings block its writes. Never create quality profiles. A source profile without a mapping is not transferred.
- Pair profile changes update qualified existing movies and series, including records with files. Profile changes do not change media paths or move files. Radarr root correction remains limited to new and fileless movies; Sonarr keeps its existing root behavior.
- A synchronization cycle plans all rules for each due target together and reuses each required instance inventory, movie-file inventory, and source episode inventory. Every incoming rule for a target remains relevant to deletion protection and cross-rule conflict checks, including rules from other pairs and units that are not due yet. Only due units authorize ordinary writes.
- If applicable rules request different target profiles, roots, or direct monitoring states for one item, skip every change to that item and protect it from deletion in that cycle. Sonarr episode monitoring combines matching episode sets across rules. A nonmatching episode does not delete a series; a multi-episode file is removed only when all its episodes share an applicable deletion authorizer.
- Unknown required file metadata is not a safe filter mismatch. Incomplete inventories block dependent deletions and episode decisions. Preserve existing Radarr and Sonarr deletion scopes; never widen deletion to series because of a new rule structure.
- `reinitialize_b` is an optional top-level multi-job setting, also available as `SYNCARR_REINITIALIZE_B` for indexed configuration. It defaults off and leaves continuous scheduling unchanged. When enabled, run every legacy job and pair once, ignore intervals, plan pair rules together by target, perform a final Radarr recovery pass, log status 0 on success or 1 if any job/recovery step failed, then emit a red warning and keep the process idle until stopped. This prevents an exit-triggered Docker restart from immediately repeating the run; a new process start runs it again while the setting remains enabled.
- The one-time Radarr recovery pass only considers fileless target movies that existed before the run and remain after normal job decisions. A source movie qualifies when it has a file and passes that incoming job or pair rule's regular source and file filters; source monitoring does not matter. If any incoming rule qualifies it, set the target movie monitored and start one search, regardless of that rule's `monitor_new_content` or `auto_search`. Normal add/update/delete rules remain unchanged, and newly added target movies are not searched again by recovery.
- A rule may map several source library root prefixes to target library roots. The longest matching prefix wins and path matching observes directory boundaries. If mappings are configured and none matches an item's source path, that item is skipped with a warning. Without mappings, `target_root_path` is used; if neither is configured, the legacy parent-directory fallback is used. For Radarr, the destination root applies to new movies and existing target movies without a file; movies with a file keep their path and root, and Syncarr never moves their media files.
- A single target may receive content from multiple source instances and pairs. The default `keep_if_any_source` delete conflict policy protects an item while any configured source rule's effective presence rule says it is present. For Radarr, presence normally requires only `hasFile: true`. A delete-enabled job or pair rule may opt into `delete_if_filter_not_matching`; then a movie with a file is present for that rule only when at least one source movie file passes its quality and custom-format filters. Profile, tag, and blacklist filters do not affect Radarr file presence. `source_rule_wins` evaluates only each delete-enabled rule's own presence set.
- Aliases for the same *arr endpoint must use one API key and one destination conflict policy.
- The `managed_only` deletion scope is the default. Legacy jobs retain `syncarr-<job-id>` tags; pair rules receive stable tags derived from pair and rule IDs. Older untagged target items are not eligible under this scope unless manually tagged. `all_missing` is an explicit scope that does not require a Syncarr tag.
- Missing-content deletion is opt-in. Radarr jobs delete missing movies. Sonarr jobs can remove target episode-file entries when a source episode loses its file or no longer matches an enabled filter, then unmonitor that episode. `delete_files` defaults to false; shared media is removed only when every live rule authorizing deletion enables it.
- Deletion is skipped for a destination when any configured source inventory needed for its conflict policy cannot be read. Filter-aware Radarr deletion also requires complete movie-file inventories and the metadata fields used by each active file filter; missing or malformed required metadata fails closed.
- Optional multi-job file filters are `source_quality_match` and custom-format modes `any`, `all`, or `score`. Quality and custom-format checks are combined on the same source file. Sonarr evaluates episode files individually; only matching episodes are monitored. Multiple jobs targeting one Sonarr series combine matching episodes as a union. Unfiltered jobs retain their prior monitoring behavior.
- Radarr and Sonarr source profile filters support the backward-compatible singular `source_profile_filter` / `source_profile_filter_id` selectors and unbounded plural `source_profile_filters` / `source_profile_filter_ids` allowlists. Plural name and ID selectors are combined with OR; names match case-insensitively. A rule must use either the singular or plural form; at pair level, a rule's choice replaces the opposite inherited form. Profile selection filters transfers but does not change Radarr's `hasFile`-based deletion presence.
- Sonarr file-filter jobs add a series only when at least one source episode file matches. Fileless and nonmatching episodes remain unmonitored. Episode matching uses season and episode numbers; newly monitored matching episodes are searched when `auto_search` is enabled.
- Multi-job mode does not expose the legacy Sonarr language-profile setting; use file-level custom-format filters when matching those formats.
- `test_run` may be global, pair-level, or rule-level. A test run performs read-only planning and does not add, update, tag, or delete content.
- In a one-time run, each legacy job and pair executes once; pair rules share their plan. If all applicable rules are in test mode, recovery, search, monitoring, and deletion plans are logged without writes. A live rule override remains live.
- Entity actions use `ENTITY`-prefixed JSON records with title, stable Arr ID, instance IDs, action, reason, file state, and selected profile changes. Pair events identify both pair and rule; legacy events keep the job ID. One-time recovery uses `update_movie_monitoring` and `search_movie` actions with reason `reinitialize_b_missing_file`. Serialize only allow-listed metadata; never log endpoint URLs, API keys, headers, or request payloads.

## Change hygiene

- Treat `syncarr/syncarr` as upstream. Work against it only when explicitly instructed, and send changes there exclusively through pull requests; never push directly to upstream branches.
- Keep credentials, live endpoint details, private media names, operational stack data, and other user-specific usage information out of tracked files.
- Update this file when project architecture or agreed multi-job behavior changes. Record only general implementation facts and decisions.


## Container publishing

- The container workflow runs the Python 3.6 unit suite and builds `linux/amd64` and `linux/arm64` on pull requests without publishing. Pushes to the default branch publish `latest`, and numeric version tags publish matching tags.
- GHCR packages are set to public after the first publish; public visibility cannot be reverted to private. Publishing uses the workflow's `GITHUB_TOKEN` with package-write permission and links images to the source repository.
- Keep local `.env` files and private runtime configuration out of Git and Docker build contexts. Compose examples use placeholders and mount runtime configuration read-only.
